# 02 — Modal de Nome de Exibição sobe com o teclado

**What to build:** ao abrir o teclado para digitar o Nome de Exibição no Desafio Diário, o modal "Escolha seu nome" sobe para não ficar atrás do teclado, mantendo ~32px de respiro entre a base do card e o topo do teclado aberto. Sem teclado aberto, o modal continua centralizado exatamente como hoje.

**Blocked by:** Nenhum — pode começar imediatamente.

**Status:** ready-for-human

- [x] `components/DisplayNameModal.tsx`: componente hoje é uma `View` absolutamente posicionada simulando overlay/modal (não usa `Modal` nativo) — a solução precisa funcionar dentro desse padrão, não assumir `Modal`. Adiciona keyboard-avoidance (ex.: `KeyboardAvoidingView` com `behavior` apropriado por plataforma, ou listener de `Keyboard` + ajuste de posição) de forma que o card suba o suficiente pra manter ~32px entre sua base e o topo do teclado. Implementado via listener manual de `Keyboard` (`keyboardWillShow`/`Hide` no iOS, `keyboardDidShow`/`Hide` no Android) guardando `keyboardHeight` em estado — não `KeyboardAvoidingView`, porque o algoritmo automático dele não garante um respiro exato de 32px (centralizar dentro do espaço encolhido produz uma folga que varia com a altura do card, não um valor fixo). Com teclado visível, o overlay troca `justifyContent: 'center'` por `'flex-end'` e ganha `paddingBottom` calculado (ver próximo item) — sem teclado, nada muda.
- [x] Checar o comportamento nativo do Android (`windowSoftInputMode`) antes de aplicar a solução, pra não duplicar o ajuste (Android por padrão já pode redimensionar a tela) — a correção deve ficar local a este componente, sem mudar `AndroidManifest`/comportamento de outras telas. Conferido no manifest já gerado pelo build (`android/app/build/.../AndroidManifest.xml`): `android:windowSoftInputMode="adjustResize"` já está setado (padrão do Expo) — a janela Android já encolhe pela altura do teclado. Por isso o `paddingBottom` aplicado é diferente por plataforma: iOS soma `keyboardHeight + 32` (nada é redimensionado sozinho ali); Android soma só os `32` fixos (a janela já encolheu até o topo do teclado, então o `bottom: 0` do overlay já cai exatamente ali — só falta o respiro extra).
- [ ] Validação manual via skill `run`: abrir o Desafio Diário, tocar no campo de nome, confirmar visualmente que o campo de texto e o botão de salvar ficam visíveis acima do teclado tanto em iOS quanto Android (ou documentar qual plataforma não pôde ser testada no ambiente disponível). **Bloqueada neste ambiente pelo mesmo motivo já documentado no ticket 02 do polish pass anterior** (`.scratch/app-polish-pass/issues/02-i18n-gaps.md`): o único build instalado no emulador disponível (`Pixel_9`) é um APK standalone com o bundle JS embutido, não um dev-client conectado ao Metro — reiniciar o Metro, forward de porta e deep-link não fazem esse build carregar código novo (confirmado na sessão anterior, mesmo emulador). Sem device iOS disponível neste ambiente Windows. Confiança no código vem de leitura cuidadosa do manifest gerado (comportamento real do Android já verificado, não suposto) e do algoritmo em si (branch por `Platform.OS`, gap calculado a partir da altura real do teclado reportada pelo evento, não um valor cru). Confirmação visual real precisa de um dev-client build novo — fora do escopo que dá pra fazer nesta sessão.
